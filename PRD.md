# PRD — project-init

## Problem (FACT — README.md, docs/adr/ADR-001)

Every new repository in the chrysa ecosystem needs the same baseline: CI/CD,
pre-commit hooks, Makefile, Dockerfile, Dependabot, SonarQube, GitHub
labels/templates, README, `.gitignore`, VS Code config, Copilot instructions,
Claude Code config, Notion bootstrap, and standardized versioning. Done by hand
this is inconsistent and drifts over time.

## Product intent (FACT — README.md)

`project-init` rationalizes project creation, enforces standards from day one,
and automates repetitive setup. It reduces drift between projects and integrates
shared standards from `chrysa/shared-standards`.

## Positioning (FACT — docs/adr/ADR-002)

`project-init` is an **orchestrator, not a generator**. It consumes the
ecosystem's published tools (`fastapi-app-generator`, `django-app-forge`,
`base-makefile`, `chrysa/github-actions`, `chrysa/pre-commit-tools`,
`chrysa-lib`, `chrysa/shared-standards`) and delegates to them; it re-implements
none of their logic. Its own code is orchestration + a manifest schema + the
glue mapping a project type to the right tools and revisions.

## Users (INFERENCE)

- Ecosystem maintainers scaffolding new chrysa repositories.
- CI, calling `update` to detect configuration drift (ADR-001 §Consequences).
- Agents/humans resolving which standards domains govern a repo.

## Product requirements

Requirement IDs are tracked in [REQUIREMENTS.md](REQUIREMENTS.md).

- **REQ-PROD-001 (FACT, implemented):** Resolve a repo's standards *profile* to
  its applicable `STD-*` domains — selection only, never copying rule text
  (`standards` CLI command; `StandardsProfileResolver`).
- **REQ-PROD-002 (FACT, partial):** Generate a project's FastAPI modules by
  delegating to the forge (`init` command → `ForgeAdapter`).
- **REQ-PROD-003 (FACT, implemented):** List supported project types
  (`list-types` command).
- **REQ-PROD-004 (FACT, planned):** `init` scaffolds a full new repo from
  scratch across all baseline concerns (ADR-001 §1). Only FastAPI-module
  delegation exists today.
- **REQ-PROD-005 (FACT, planned):** `update` applies missing pieces to an
  existing repo, non-destructively and idempotently, with a merge strategy that
  never silently overwrites locally-modified files (ADR-001 §4).
- **REQ-PROD-006 (FACT, planned):** Support additional project types
  (`react19`, `python-cli`, `python-library`, `gas`, `monorepo`, `generic`) —
  all marked Planned in ADR-001 and README.
- **REQ-PROD-007 (FACT, planned):** Optional `extras` modules — GitHub bootstrap
  (labels/templates/Dependabot), Notion bootstrap, SonarQube registration
  (ADR-001 §5 hooks; README issues #5, #8).

## Out of scope (FACT — ADR-002)

Re-implementing app/module generation, Makefiles, CI job logic, commit-gate
hooks, auth/config/logging, or the design system. Those belong to the consumed
tools.

## Status (FACT — README.md)

Early planning phase. Standards-profile resolution and FastAPI-module delegation
are the built slices; the general scaffolding engine and most project types are
planned. See the repo issues (#1–#9) for the work breakdown.
